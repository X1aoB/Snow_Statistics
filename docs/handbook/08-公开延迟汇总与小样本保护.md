# 08 公开延迟汇总与小样本保护

## 为什么内部精确值不能直接公开

低流量站的一条失败请求、一次角色选择都可能与具体访问行为过于接近。公开页因此读取单独的发布投影，不读取内部精确daily、原始事件或Doris明细。内部仍保留精确口径，以便对账；公开层采用延迟、分组抑制和冻结历史，降低小计数暴露。

当前候选每天香港00:15形成发布批次；日期D在D+3日00:15达到发布截止。比如9月13日的数据最早在9月16日00:15公开。截止之前仍显示pending，不将等待发布显示成无用户。公开历史自投影安装日起建立；旧精确汇总缺少新保护规则所需的辅助证据，不能凭空补出“已满足门槛”的历史。

```text
内部精确数据 → 截止前候选累计 → 每应用/日期首次冻结
             → access / quality / popularity分别判定
             → published有值；pending/empty/suppressed为null
```

## 三组数据的判定

访问组依赖至少10个有效应用内日匿名标识。质量组要求至少10个已记录生成请求，且成功数和失败数分别为0或至少10。热度组需要其每个分类有至少10个独立访问标识，否则整组抑制。最终精确规则请对照 `public_projection.py`，不能用教程中的自然语言替代实现检查。

为什么99成功/100请求要一起隐藏？因为请求量减成功数就得到1失败。只遮住失败字段没有效果；成功率和分母也能重建它。热度同样不能只隐藏一个小分类，却留下总量和其他分类供相减。

10只是发布阈值，不是完全匿名保证。服务质量记录没有匿名用户标识，10次请求可能来自同一人。浏览器标识也不等同经过认证的自然人。

## v1与v2

公开v2按指标组提供state和value：published是可发布值；empty是真实无该类记录；suppressed是未达到条件；pending是未到发布时间。只有published带数值。客户端不应自行把null转换为0。

v1保留既有字段；由于PV/UV/请求等是必填整数，无法部分置空，故采用更保守的整行省略。不能留下一个未经投影的旧v1端点来绕过新页面。

公开快照超过26小时未生成则显示stale。页面每分钟重新判断过期，可见时有限刷新。快照已冻结后，内部迟到校正不反复改公开日值，避免通过比较连续版本看见很小的增量。归档必须保留原生成时间。

## 操作与练习

```powershell
node --test adapters/browser/public-summary.test.mjs
Get-Content contracts/v2/summary.schema.json
```

若当前检出还没有v2文件，应更新到验收候选后学习，不把不存在的接口当作已上线。线上检查只访问聚合路由；不要为了看隐藏数字去找原始API。

练习：访问组已满足条件，质量只有3请求，v2和v1应如何显示？

答案：v2可显示访问组，质量state=suppressed、value=null；v1因无法表达局部隐藏，应省略这一整行。页面说明缺失不等于零。内部daily的3仍存在，不能为了公开展示方便把它改成0。

2026-09-19正式启用后，独立执行67项纯GET公网复验，所有检查通过。额外当前日检查确认：summary v1/v2整体为ok、no-store且生成时间满足策略，两应用今天的三组字段均为pending并以null表达尚未发布，v1没有今天的行。私有接口继续404，许可来源CORS边界正确。

与此同时，内部已经接收验收人员通过真实浏览器产生的少量操作，接收与聚合进度一致。本手册不复制这些真实小样本计数和位点。这不构成“公开统计出错”：内部精确计数与对外延迟投影本来就不同。页面不能把pending/null渲染成0，也不能为了演示热度而提前展示今日精确计数。这个小样本观察证明本次公开状态按规则隐藏未发布时间的数据；它不证明k阈值提供数学意义的匿名保证，也不是跨期攻击的完整证明。


## 排障案例：公开页正常，为什么质量链路仍可能有问题

9月19日16:27香港的一次只读观察中，collector仍健康，公开汇总也能正常返回，但独立日志forwarder的累计failures已经达到33。reader和forwarder都显示active、没有重启；reader的spool为0条，完成日志ACK也是0。于是不能只看进程“绿灯”或公开接口200就宣布整条质量链路正常，更不能把ACK0解释成“所有用户请求失败”。这里根本没有本次验收产生的付费生成完成请求。

8次只读取白名单协议的socket探测提供了更具体的证据：多数约0.001秒，第6次在3.002秒超时，下一次约1.005秒。源码显示原reader主线程先执行可能持续数十秒的Docker轮询，再回到socket.accept；forwarder只等待3秒，遇到轮询窗口就可能超时。证据支持“读取端阻塞响应”的定位，但没有逐次异常明细就不把全部33次累计失败断言为完全相同的原因。

16:36:12香港正式修复完成：单个后台任务执行有界轮询，主线程继续提供已提交的投影批次。45秒观察窗口内实际完成113次AF_UNIX探测，最大响应0.045秒，没有新增forwarder失败；修复开始时累计失败已为37，完成后仍为37，历史没有清零。reader失败和incomplete仍为0，质量ACK仍为0。

对公开统计的正确解读是：公开投影的时间、小样本与状态规则照常执行，运维失败计数属于私有链路状态，不塞进公开请求失败率。`forwarder.failures=37`既不等于37次聊天失败，也不等于丢失37条事件；它是该进程捕获异常的累计次数。质量成功率必须来自已记录且去重的可信request_complete事件，不能拿socket重试次数当分母。

这次空spool下的短窗口延迟测量证明了所观察的响应问题得到改善，不是有真实生成负载时的吞吐压测，也不能代替生成完成到collector的端到端投递验收。
