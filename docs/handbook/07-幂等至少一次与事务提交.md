# 07 幂等、至少一次与事务提交

## 先用转账通知类比

如果发送端没有收到响应，它不知道服务端是没执行，还是执行后响应丢了。直接重试可能重复操作；不重试可能漏操作。数据工程常见的做法是允许重放，用稳定业务键让重复执行得到同一结果，即幂等。不能因为系统用了Kafka或Checkpoint就直接宣布端到端恰好一次。

本项目有三个常见键：event_id代表一次不可变事件，request_id代表一次业务生成请求，seq代表collector中接受记录的单调位点。Kafka的topic/partition/offset表示传输位置，不是业务请求身份。一条旧事件重放到新的Kafka offset，仍然是同一个event_id。

```text
接收：event_id＋内容指纹 → 相同内容重复确认／不同内容冲突拒绝
请求：source＋app＋request_id → 首次接受的可信完成成为赢家
聚合：读位点 → 计数更新＋写新位点 → 同一个事务commit
同步：归档fsync → Kafka确认 → 推进私有读取位点
```

## 为什么位点与计数必须同事务

假设先把PV加10，再单独更新位点，二者之间崩溃会导致恢复后再次处理同样10条，PV多10。若先更新位点再加PV，崩溃则会漏10。放进同一个SQLite事务，要么一起成功，要么一起回滚，消除这个内部窗口。

这不自动覆盖其他系统。collector与Kafka之间没有一个跨系统数据库事务，因此可靠同步先把原批次写到本地并校验，然后发送Kafka；确认丢失时可重放。后续DWD继续按事件和请求键去重。每一层都要明确“哪个时刻以后算承诺了什么”。

## 冲突与真正重复不同

同一个event_id、完全相同内容叫重放；同一个event_id但success从false改成true是内容冲突，不能悄悄当新版覆盖。v1事件设计是不可变事实。确需业务修改应使用有版本的CDC/业务变更模型，而不是复用不可变事件ID修改旧事实。

## 具体练习

阅读接收与恢复测试：

```powershell
uv run pytest -q tests/test_acceptance.py
Get-Content src/snow_statistics/sync.py
```

画出“Kafka已确认，客户端保存位点之前崩溃”这一时刻。恢复后应读同一个已归档批次，允许再次投递；不能直接丢弃归档或把位点跳到最新。

验收不能只看最终行数：要同时保留原始数、有效数、重复数、隔离数、截止时间后记录数；说明重复在哪里被识别。`raw=valid+duplicates+quarantined+after_cutoff` 是质量账本，source范围和过滤顺序必须一致。

练习答案：即使Kafka确认丢失造成第二次投递，DWD的event_id不变，因此日指标不增加；Kafkaoffset和原始消息计数可能增加。这正是“传输至少一次＋业务幂等”与“所有层原始行都只出现一次”的区别。
