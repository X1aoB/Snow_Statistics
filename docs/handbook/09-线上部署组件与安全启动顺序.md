# 09 线上部署组件与安全启动顺序

## 线上到底需要什么

正式基础统计只需独立collector、SQLite配额存储、受控网关、专用Tunnel及脱敏日志读取/转发器。本机Kafka、Hadoop、Doris等不常驻线上。域名确定为 `stats.xiaob.dev`；两个产品仍分别通过自己的发布流程交付。

```text
浏览器HTTPS → stats.xiaob.dev Tunnel → gateway → 回环collector
业务Docker日志 → root只读reader → 白名单spool/socket → 低权限forwarder → 回环collector
本机维护者 → SSH隧道 → 私有增量读取
```

候选的资源上限：collector 256MiB/0.25CPU，gateway 64MiB/0.10CPU，Tunnel 128MiB/0.10CPU，reader和forwarder各64MiB/0.10CPU，总上限约576MiB/0.65CPU。这是配置限制，不是测得的常驻内存。collector独立512MiB文件系统；reader独立16MiB spool，还要计入回滚日志等短时空间。

## 启动顺序不能倒过来

1. 确认本次代码、镜像与依赖锁身份；读取宿主容量和现有业务蓝绿版本，不覆盖未知发布。
2. 准备只属于本项目的新目录和配额文件系统。已有数据或挂载不允许重新格式化。
3. 先安装/核对持久mount，再用off模式启动collector。没有挂载时必须拒绝启动，避免数据写入挂载点下面的普通目录。
4. 在回环8110端口验证gateway候选，Host设为stats.xiaob.dev；只暴露事件和公开v1/v2汇总。
5. 单独配置Tunnel和DNS/TLS；私有读取、health、docs及任意SQL不暴露公网。
6. 产品完成告知与候选回归后，才按正式发布回执逐步启用；日志转发此前保持关闭。

## 先学只读计划，不盲目安装

```powershell
uv run python tools/production_install.py --help
```

真正安装工具的Linux参数、root目录检查和计划SHA以 `deploy/production/README.md` 为准。`plan`产生审查清单，`install --expected-plan-sha256 ...`只安装明确文件并重读systemd，不意味着已创建文件系统、启用服务、修改DNS或切流。不要把“安装器exit 0”当成“正式系统上线”。

server token和reader token必须不同。token存私有文件，用受限凭据机制交给进程，不能出现在浏览器config、截图、Git、手册命令行或日志里。转发器不持有Docker socket/group权限；reader只执行固定只读Docker操作。

## 验收与常见失败

检查正向HTTPS/CORS，也检查反向边界：访问private/health/docs应404；公共入口剥离Authorization/Cookie/IP/Referer，不能借公网冒充可信完成。collector异常时gateway失败应隔离于主站和聊天。

挂载失败先停collector并核对mount单元，不在写入中卸载。401先分清server与reader凭据是否混用；不要把token打印出来比对。公网有交互挑战时，采集请求可能被挑战页替代，必须修正精确路由策略，而不是在浏览器盲目无限重试。

练习答案：如果在没有quota挂载时允许Docker自启，SQLite可能写入宿主根分区，表面正常却绕过预算。因此本项目启动门禁检查真实mount，容器重启策略也不能绕过它。

## 9月19日轻量采集正式启用：精确边界与检查结果

完成两站发布、告知与公网检查后，协调者审阅具体独立计划并授权执行。2026-09-19 14:07:42至14:08:25香港，执行器仅把SNOW_MODE从off改为lite、把SNOW_LOG_FORWARD_ENABLED从false改为true，并启用已安装的reader/forwarder。它没有修改产品容器、Caddy业务路由、业务数据库、共享embedding、collector镜像或凭据；256MiB/0.25CPU、配额挂载、回环端口等保持不变。

启动先确认collector健康及公开汇总ok/empty，再启动reader，等待本次新poll和UNIX socket就绪后才启动forwarder。这个等待避免首次连接reader尚未就绪时产生失败计数。两者实际均enabled/active、重启0、失败0、不完整poll0。公开v1/v2为200/ok；网关private/status/health/docs仍404。事件数、接收位点、聚合位点在启用回执时均0；没有主动注入任何事件，也没有调用付费模型。日志ACK增量为0，所以只确认了空载进程与进度可用，没有伪称本次已有真实请求成功投递。

计划对root私有.env与server-token做0600检查；server和reader凭据不同，forwarder的LoadCredential文件与collector服务端凭据在内存中比较相同，不输出值或把它们复制到本手册。转发器用户不属于docker、sudo或root组。原有日志读取回看600秒，spool和游标属于本项目；新启用不代表全历史完整，覆盖缺口计数需要持续查看。

执行失败会分别尝试停止及禁用自己的两个日志unit，再恢复自己的off配置和collector。任一stop失败仍继续其他步骤；并行业务重启不会阻止关闭统计。若配置已被另一个明确变更更新，拒绝覆写新配置并保留recovery-incomplete收据。所有恢复只停止新增采集，不删除已确认的事件、spool或游标。使用该次plan的rollback/recover是有边界的恢复操作，不应把已过期的历史apply命令作为今后通用启用命令复制执行。

学习时区分三层证据：14个合成恢复/漂移/启动顺序测试证明工具分支行为；生产apply回执证明这次变更及空载状态；启用后的浏览器和真实完成事件回执才证明实际业务采集。三者不能互相替代。
