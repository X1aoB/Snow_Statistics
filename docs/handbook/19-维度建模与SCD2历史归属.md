## 事实和维度的区别

事实描述发生了什么、多少次、多少秒；维度描述事实发生时的对象属性，例如内容属于哪个分类、活动属于哪个渠道。把事实与维度分开，能够复用描述并处理属性变化。维度建模不是看到星形图就结束，首先要确定事实粒度、业务主键、版本和时间关联规则。

SCD2把同一实体的不同历史状态保存成多行，每行有valid_from、valid_to。项目采用左闭右开区间 `[valid_from, valid_to)`：变更时刻属于新版本，不同时属于旧新两行。

```text
文章content-1
版本1 data：       [1月1日00:00, 1月2日00:00)
版本2 engineering：[1月2日00:00, +∞)
事实在1月1日 → data；事实在1月2日恰好00:00 → engineering
```

## 历史归属与当前重组

按发生时分类的报表回答“当时这个分类表现怎样”；按当前分类重组回答“现在归到这个分类的内容过去表现怎样”。两者都可能有用，但不能把后者覆盖前者。若文章从数据分类移到工程分类，历史报表不应毫无说明地跟着移动。

合成demo已有content-1从data到engineering的变化，还含内容删除。删除通过墓碑关闭或终止当前成员关系，历史有效区间仍保留。直接物理删除所有旧维度行会使历史事实Join不到属性。

## SQL关联的关键条件

```sql
SELECT f.event_id, d.category
FROM facts f
LEFT JOIN dim_content_scd2 d
  ON f.content_id=d.content_id
 AND f.occurred_at>=d.valid_from
 AND (d.valid_to IS NULL OR f.occurred_at<d.valid_to);
```

这是教学字段示意；实际表的字段和attributes展开方式以ops.py为准。验证每条有效事实最多关联一行维度；若某事实Join出两行，可能是区间重叠、边界使用BETWEEN或业务键不完整。LEFT JOIN保留无法匹配的事实，便于作为质量问题查看，不能先INNER JOIN把问题记录悄悄丢掉。

## 从目录快照到真正的维度作业，还差什么

已有快照只解决了“这份公开目录来自哪个已发布产品版本”。要宣称真实 SCD2 和事实关联已经完成，还需要以下实际作业证据：

1. 明确页面或角色的应用内业务键，保留 `app`，不能把两个应用相同字符串的 ID 直接合并。
2. 明确纳入历史追踪的属性、删除语义与可靠的生效时间来源；相同属性的重复发布不能生成重叠区间。
3. 在作业输入和输出回执中记录 `snapshot_id`、源提交、文件 SHA，以及实际目标表和运行身份；保留原始有效时间，不因重跑刷新。
4. 用事实的 `occurred_at` 关联维度区间，并实际检查零匹配、多匹配及重复事实。目录存在不代表该事实一定有可证明的历史分类。
5. 另行实现按当前分类重组的查询，并清楚标记其口径；它不能覆盖按发生时归属的历史报表。

当前应表述为“已准备并验证两版已发布公共目录输入；真实维度落表、区间构建和事实 JOIN 仍需独立作业验收”。合成 demo 的 SCD2 成绩也要单独描述，不能替代真实数据上的验收。业务产品构建始终独立，不反向导入数仓仓库。
