# 02 三种运行模式与解耦边界

## 为什么要把功能设计成可以拆掉

这个项目既服务求职学习，也要允许未来只留下一个低成本统计页。假如个人站构建必须连接 Doris，电脑关机就会导致上线失败；假如聊天处理必须等待 Kafka，实验系统故障就会拖垮产品。因此“解耦”不是写一句微服务，而是让启动、构建、运行、测试、发布、资源和数据所有权都有可验证的分界。

| 模式 | 运行的东西 | 基础统计从哪里来 |
|---|---|---|
| full | 轻量服务，加按需开启的本机数仓 | 始终由轻量服务生成 |
| lite | 采集、SQLite、基础聚合、公开投影 | 同一份轻量数据 |
| off | 拒绝新事件，保留明确归档或移除页面 | 归档结果，不制造新零值 |

```text
业务页面/聊天 —— 独立发布
        └── 可选统计适配 —— 失败可以丢弃
轻量统计 —— 独立数据库、独立配额
        └── 本机消费者 —— 可以暂停，但要认识保留期缺口
```

`SNOW_MODE=full` 不会自动启动 VMware；`SNOW_MODE=off` 也不会替你修改两个产品的公开 config.mjs。这两个开关在不同发布边界，操作时必须分开核对。用户在浏览器撤销同意又是第三种开关，它只影响该来源的浏览器访问事件，不等于停掉线上服务质量统计。

## 自己验证默认关闭

```powershell
uv run snow-stats serve --host 127.0.0.1 --port 8100
```

新终端读取：

```powershell
Invoke-RestMethod 'http://127.0.0.1:8100/healthz'
```

未设置 SNOW_MODE 时应显示 mode=off。这里只启动本机回环服务，不连接生产；结束时回到服务终端按 Ctrl+C 正常关闭。若8100已被自己的测试服务使用，先确认进程用途，再换8101等未占用端口，不盲目终止任意占用者。

## “独立”要看哪些证据

产品自己的仓库保存适配器副本，不从 `../Snow_Statistics` 导入代码。产品CI只检出产品仓库；主站页面在运行时读公开JSON，构建时不请求统计服务。聊天请求/签名、IndexedDB、业务表不存统计偏好。统计服务的SQLite、日志spool、配置、代理入口和卷都登记在本项目资源清单里。

共享宿主仍存在共同故障边界：服务器断电会影响同机多个服务。容器解耦不能把一个物理宿主变成物理容灾。我们通过资源上限和失败隔离降低相互拖累，而不夸大边界。

## 练习与答案

练习：把三台VM全部关闭，公开页应该立即显示“系统已关闭”吗？

答案：不应该。VM属于实验数仓，轻量服务仍能接收、聚合并按公开发布节奏更新JSON。若公开数据还没到延迟发布时间，页面应显示等待；若该日期样本不足，显示抑制。不能把“数仓未运行”误判为“线上统计故障”。

故障练习可用独立合成服务返回503，然后观察聊天仍成功。切勿把生产collector改成故障状态作为随手练习。
