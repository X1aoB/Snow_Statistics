### 先用白话理解

一次事件有“发生时间”和“接收时间”，还有提交后的序号。窗口恢复要证明读的是同一个来源、没有静默跳过缺失序号，并让每份副本继承原接收时间的期限。当前实现的 accepted_at 在取得写锁之前生成，因此接收时间不保证随提交序号单调；仅看第一条记录的时间不够。固定序号前缀是已提交记录的边界，不是穷尽某个墙上时钟时刻所有排队请求的水位。

```text
原始保留期已过 → 清理登记到期副本 → 只读status固定源身份和末端
→ 有限分页核验连续seq → 按原accepted_at选择连续后缀
→ 记录不可恢复缺口与主动省略范围 → 新lane登记 → 实际同步与对账
```

### 合成手算：为什么不能只取第一条时间

假设只选择某个合成日期00:00之后的输入，按序号得到101（00:05）、102（前日23:59）、103（00:20）、104（00:10）。由于序号102仍属于旧时间范围，连续后缀从103开始，新的after是102；该后缀的最早接收时间是104的00:10，而不是103的00:20。因此期限是原00:10加7天，复制或重放不能重新起算。序号101虽然时间较新，但位于主动省略前缀内，必须记录省略，不能假称全部保留记录已导入。这些数字全部是教学合成例子。

### 检查、失败处理与练习

检查固定末端、源instance/generation及最后的保留边界是否一致；检查使用的是连续后缀的最早accepted_at，而非“现在”。遇到410或源变更，停止该次操作、保留元数据证据，再显式选择新起点。来源接口不可达不等于零事件；从源末端读取为空也不证明本地仓库已追平。公开页的pending／suppressed与本地计算是否完整是不同判断。

练习：把合成序号104的接收时间改为前日23:58，后缀还有可用事件吗？答案：没有；返回no_input并保持原进度，不能把截止改成现在生成空日报。面试追问：为什么按seq推进同时仍校验accepted_at？前者保证已提交连续前缀与重放边界，后者保证数据保留期限和时间窗口不被复制重置。

## 电脑关机时会发生什么

线上轻量统计继续运行，本机Kafka与数仓可以停止。重新开机后，本机通过受控私有增量接口读取尚在保留期内的事件。原始事件暂存目标7天，因此关机超过保留窗口可能无法完整补回；不能在教程中把“支持增量同步”写成“任意时长离线都绝不丢历史”。

真实数据按需处理与合成实验分开：real目录、主题、HDFS路径、Doris数据库和私有发布包都要隔离。真实运营分析只解释真实发生的事件；合成内容状态机、工单和CDC模型用于学习，不能把它们混进真实业务看板。

```text
collector私有seq → 本地批次+校验和 → Kafka确认 → 同步位点
→ 冻结ODS清单 → 内部真实日指标/行为模型 → 私有发布包
```

## 接口和命令含义

私有 `GET /analytics/private/v1/events?after=...&limit=...` 返回单调序号信封与下一位点。after表示“从这个已知接受位点之后继续”，不是业务日期。limit是批次上限，不是总共只处理这些数据。接口需要独立reader凭据，只通过SSH隧道访问，公网网关不路由它。

2026-09-19旧epoch的历史同步使用受控 `run-real-storage-windows-v3.py sync` 的 inspect／execute 两步；它在受控guest中调用原冻结业务逻辑。裸 `tools/real_lab.py --config … sync` 留作机制参考，不承担当前Windows进程/VM收尾边界。底层 `snow-stats sync` 的参数可以用于阅读实现和隔离合成实验，但它不是本项目正式 writer 的操作入口：通用 CLI 不会替你检查 epoch 写入窗口、恢复登记和当前 Flink 作业。原统一业务入口负责这些检查与整批操作锁、逐条原接收时间校验，外层受控storage还负责现场身份、资源、进程和精确收尾。不要因为某个底层命令能发送消息，就绕开正式入口使用它。

```powershell

uv run python tools/real_lab.py --config runtime/real/config/run.json sync --describe
```

`--describe`通过表示配置结构与执行节点合法，不表示凭据、Kafka、清理或真实writer已经通过。以下首次配置／初始化供全新lane参考；同一有效epoch已经登记过时不能重复创建，但旧epoch过期后需要新lane的实际初始化。后面的storage V3为历史固定窗口参考，不用于本轮新epoch。早先正式实时前缀与恢复有实际证据，新6c60路线的阶段必须有自己的回执。

|---|---|---|
| `runtime/real/config/run.json` | 从仓库模板复制，填写实际私网IP、既定lane、私有文件相对路径 | 只是操作配置，不含验收结论 |

在编辑器中逐项填写。`source`和`input_origin`正式都为`real`；`transport_node`固定`snow-analysis`；三个nodes是三个不同的实际私有IPv4；collector_url只允许带端口的`http://127.0.0.1`，通过SSH转发到服务器自身8100。lane是已准备epoch的同名标识，3–24个小写字母/数字/连字符且以字母开头。事件topic中的lane将连字符转为下划线，不截断。不要把示例lane、示例IP或`.invalid`主机名照搬到实际运行。

将同一run.json放到各VM的相同相对路径。新环境先在各VM创建 `runtime/real/config`；Windows使用 `lab_remote.py --node snow-control --upload runtime/real/config/run.json --remote /home/snow/Snow_Statistics/runtime/real/config/run.json`，其他两节点同理。不要把Windows私钥或token夹进源码包。analysis上的token、key、known-hosts与私有JSON必须为普通文件、无符号链接、权限0600；上级私有目录用0700。Windows的本机ACL与Linux0600是两套权限，不能只在Windows chmod的心理模型下理解。

### 初始化做了一半怎么办

一次初始化可能已经创建空表和账号，却在最后检查时失败。这个时候，“再执行一次初始化”可能覆盖线索或重复创建资源，不能作为通用处理方法。本项目保存原始`initializing.json`和账号，先查实际Topic位点、表行数、作业、Checkpoint和Docker身份，再决定能否补齐登记。

9月19日遇到的具体问题是：Flink启动时会自动解包两个RPC JAR，并生成两份默认JAAS配置。它们出现在状态卷中，但不是用户事件或Checkpoint。`63a0d415a938b077be0dde5c5501e386720392fe`加入了固定内容核验，只有锁定版本、尺寸、SHA256、权限和所属用户完全符合预期的四个文件才被接受；任意额外文件或旧作业仍被拒绝。这个修复的Linux CI已通过，实际恢复结果须另看运行回执。

独立恢复命令是`tools/real_writer.py ... finalize-initialization`，执行位置仍为analysis；它要求受控的collector回环隧道已经建立，使用原epoch和reader token文件。该命令不创建账号、不重跑DDL、不改原到期时间，而是通过实时读回完成不可变登记。完整参数及限制见[仓库恢复操作说明](../real-lab-runner.md)。它不是日常启动命令，不能用于已有作业、已有数据或Checkpoint恢复；日常仍走第24章。

## 日常一次同步：有数据继续，无数据停止当前计算路线

前置条件为：原epoch未到期、同版本writer实际运行、没有未解决gap、私有通路有效；若刚开机，先执行[第24章的正常恢复](24-Flink水位线Checkpoint与迟到修正.md)。同步入口只进行本次有界读取，不让后台任务无限排队。

```powershell
# Windows；第1行生成本次 sync scope，在线读取实际guest元数据
& ./.venv/Scripts/python.exe runtime/real/operator/run-real-storage-windows-v3.py sync
# 核对本次scope后才执行；占位符必须替换为上一步真实输出，不能复制旧scope
& ./.venv/Scripts/python.exe runtime/real/operator/run-real-storage-windows-v3.py sync --execute --scope runtime/real/operator/storage-v3-scope-<本次32位ID>.json
```

每行检查 `$LASTEXITCODE`。sync完成后另对`capture`生成对应scope并执行，不能复用sync的scope。capture允许明确检验过的两种状态：原writer已resumed且实时引擎运行，或writer完整paused且两个Flink已停；不能凭“Kafka在线”自行猜测状态。

sync在复制新批次之前、重放之前和逐条发送之前检查原始accepted_at与epoch窗口，Kafka确认后才推进collector位点。capture冻结Kafka范围并保存校验批次，不推进Kafka消费者位点。`no_new_input`/`no_input`表示当前没有可处理新增输入，不生成一组零指标，也不反复往正式collector灌测试数据。窗口下界不符、过期、410或变代立即停，保留归档及缺口记录；不要编辑cursor强行继续。

**2026-09-26 实际失败样例：** storage V3 的 inspect/execute 两步先确认了 analysis 4608 MiB、writer resumed、Flink 运行和真实 source 身份；`sync` 没有生成成功回执，外层只记录 `NodeCommandFailure`，随后精确停止 epoch 与 VM。失败回执 `runtime/real/operator/storage-v3/a7fb22a2fb704b0799e107ad36ee97bc/finished.json` 保留在本机忽略目录。窗口关闭后经独立 SSH 隧道只读读取 status 得到 HTTP 200，accepted 与 aggregate 末端一致；从该末端继续读取返回零事件，未读取事件正文。这只排除了当时collector明显不可达及聚合位点落后；从源末端读取为空不能证明本地同步位点已经到达该末端，也不能推断guest sync的具体异常。下一次候选应先保留阶段失败类型和返回码，再决定是否重试；不能用一次退出码或“没有新事件”替代 Kafka ACK、ODS coverage 或闭日完整性。

有capture批次时，后续先正常暂停writer，再切离线HDFS运行land，实际HDFS落地读回后回存储阶段ack；本次固定首闭日必须先ACK、登记coverage，再进入模型计算。完整阶段顺序和命令在[第30章](30-日常运维备份精简与移除.md)。这里刻意不提供通用CLI直接连接真实Kafka的替代办法，避免遗漏门禁。

## 已验证的独立SSH读取账户

2026-09-13，协调者已实际部署并验证`tools/private_access.py`管理的`snow_stats_reader`。它只允许向服务器自身`127.0.0.1:8100`做本地TCP转发，不能登录Shell、SFTP、执行命令、分配终端、转发其他端口或建立远程转发。`MaxSessions 0`限制SSH会话，不等于禁用已允许的TCP转发。reader token仍是第二层接口鉴权：有SSH公钥不代表可以不带token读取事件。

实际验收中，私有status携reader token返回200、无token返回401；Shell/SFTP/其他端口/远程转发均被拒绝；root/deploy的有效SSH策略前后相同。正式collector位点仍为0，没有为这次验证注入正式事件。这个结论证明私有连接和鉴权边界，不代表公网Tunnel、浏览器采集或真实数仓已经启用。服务器地址、密钥、token和collector实际代际不写进手册。

### 新环境如何准备专用密钥

当前这台电脑已有专用密钥，**不要重跑生成命令覆盖它**。以下是新环境从零创建的示例，Python先检查两个目标不存在，并以参数列表传递空口令；它不会把私钥打印出来。无人值守空口令密钥须用本机访问权限保护，且不能复用业务root私钥。

```powershell
@'
from pathlib import Path
import subprocess
key = Path('runtime/real/ssh/collector.key')
if key.exists() or key.with_suffix(key.suffix + '.pub').exists():
    raise SystemExit('已有密钥，停止；请使用既有配置或单独设计轮换')
key.parent.mkdir(parents=True, exist_ok=True)
subprocess.run(['ssh-keygen', '-q', '-t', 'ed25519', '-N', '', '-f', str(key)], check=True)
print('专用密钥已创建；只分发 .pub 公钥')
'@ | uv run python -

uv run python tools/private_access.py plan --public-key-file runtime/real/ssh/collector.key.pub
```

PowerShell向原生命令传空字符串的行为容易与普通字符串理解混淆，因此示例交给Python参数列表处理；不要用包含两个引号字符的字符串冒充空口令。另一种清楚的方式是交互运行ssh-keygen并在口令处按提示输入。公钥plan只生成审阅清单；正式安装必须在root控制的`/opt/snow-statistics`使用同一公钥与精确plan哈希。安装器拒绝接管已有同名账户或覆盖现有配置，不能把“再安装一次”当密钥轮换流程。

### 从Windows建立只供本机使用的隧道

先通过受控渠道保存已验证服务器host key；不能用`StrictHostKeyChecking=no`回避校验。下面的地址与端口由操作者交互输入，18100只是示例本机端口，不是把服务器collector开放到公网。

```powershell
$readerHost = Read-Host '输入已核对的服务器主机名'
$readerPort = Read-Host '输入已核对的SSH端口'
$readerKey = (Resolve-Path runtime/real/ssh/collector.key).Path
$readerKnownHosts = (Resolve-Path runtime/real/ssh/collector.known_hosts).Path
ssh -p $readerPort -i $readerKey -o "UserKnownHostsFile=$readerKnownHosts" `
  -o StrictHostKeyChecking=yes -o ExitOnForwardFailure=yes `
  -N -L '127.0.0.1:18100:127.0.0.1:8100' "snow_stats_reader@$readerHost"
```

该命令占用当前终端是正常的；`-N`表示不请求远程Shell。保持它运行，再开第二个PowerShell窗口进行读取。用Ctrl+C关闭隧道不会删除服务端数据库、SSH账户或本地同步位点。

在第二个窗口，只把reader token读入当前进程环境，不写入命令行字面量或用户级环境配置。下面只输出HTTP状态码，不输出私有status正文中的代际等信息：

```powershell
$env:SNOW_READER_TOKEN = (Get-Content runtime/real/secrets/reader.token -Raw).Trim()
try {
  @'
import os, urllib.request
request = urllib.request.Request('http://127.0.0.1:18100/analytics/private/v1/status',
    headers={'Authorization': 'Bearer ' + os.environ['SNOW_READER_TOKEN']})
with urllib.request.urlopen(request, timeout=10) as response:
    print('private_status_http=', response.status)
'@ | uv run python -
} finally {
  Remove-Item Env:\SNOW_READER_TOKEN -ErrorAction SilentlyContinue
}
```

预期为200。连接失败先检查隧道进程、host key和本地端口占用；401检查是否错用了server token；“administratively prohibited”通常表示转发目标违反了仅8100的限制，不要扩大服务器允许端口。这一手动通路只用于HTTP状态诊断；正式同步使用上面的real_lab入口自行建立和关闭analysis隧道，不能把此窗口与底层sync拼成绕过writer的通路。

## 为什么先归档再发Kafka

2026-09-19实际续作补充：签名版本`63a0d415`在正式epoch完成私有同步、Kafka确认、Flink/Doris读回，并与线上SQLite按相同已接受前缀对账。随后在Checkpoint 24暂停、停止五个引擎、整台VM软关机，再启动原容器并从同一Checkpoint恢复；实际REST恢复身份和指标均核验一致。这里的Checkpoint编号是引擎状态编号，不是事件数量或用户数量。该成绩不包含尚未完成的真实HDFS离线链或生产P95。

同步命令结束后立刻再开相同本地转发端口，曾遇到`EADDRINUSE`。当时没有存活监听者，只有内核`TIME_WAIT`；等待自然释放后恢复。排查时分别检查LISTEN和TIME_WAIT，不要看到“端口占用”就杀掉未知进程、关闭host-key检查或改用业务SSH账号。例行操作应串行执行并留出端口释放时间。

如果直接读API发Kafka，响应丢失和中途崩溃会使你难以知道某一批到底发了什么。先保存原批次和校验和，恢复时可以重放同样内容。只有Kafka确认后再推进同步位点。重放可能增加传输消息数，DWD按业务键去重后指标不应增加。

接口返回410意味着请求位点已过保留界限。此时必须识别缺失范围并形成观察不完整记录；不能静默跳到当前第一条，再给出100%完整的留存报表。重置位点需要说明从何时重新建立可观察窗口。

## 有限保留如何影响留存

真实候选的cohort定义为“保留的30天窗口中首次观察”，不是账号注册日，也不是完整生命周期的新用户。D1/D7除了等观察日期结束，还要确认对应期间的已接受前缀覆盖。如果有缺口，分母保持0、留存人数null并标明不完整，不能把缺失日当成没人回访。

真实事件归档、Kafka副本、HDFS明细、Checkpoint与备份也受保留边界约束；只清collector而无限留本机副本并不满足同一数据保留承诺。清理应依据具体real资源清单，不能误删synthetic面试成果或业务数据。

## 练习与排错

问题：本机关机10天，collector只保留7天，能否根据每日聚合重建D7留存？答案：不能。日UV丢失了跨日期匿名标识的交集；每天多少人无法告诉你是不是同一批人。可以继续展示线上精确日聚合，但真实cohort分析必须标记观察缺口。

若私有读取401，检查凭据角色；410检查已保留归档和覆盖清单；Kafka拒绝连接检查实际NAT与advertised.listeners；不要把这三种错误都用“重试直到成功”解决。
