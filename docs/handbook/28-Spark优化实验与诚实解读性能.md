# 28 Spark优化实验与诚实解读性能

## 优化先证明结果一样

一次优化应同时回答三个问题：输出是否等价、耗时或资源是否改善、条件能否重现。SQL改写后快了但漏掉一半数据不是优化。只运行一次也难以区分缓存、启动、调度和随机波动。

本项目使用90万条有效DWD，在Spark3.5.7 on YARN、VM2/2/1 GiB、一个512 MiB单核executor下做七类查询。每种配置运行三轮，第二轮反向顺序，清理Spark缓存但不清操作系统/HDFS缓存，记录输入、执行计划、任务I/O和中位数。AQE关闭、broadcast阈值-1、shuffle分区4是对照条件，不是给所有生产环境推荐的固定值。

```mermaid
flowchart LR
  B[固定输入与参数] --> E[基线和改写]
  E --> V[双向exceptAll检查]
  V --> R[多轮运行与执行计划]
  R --> C[同条件中位数和资源解释]
```

## 四个实际结论

| 实验 | 基线中位秒 | 改写中位秒 | 已观察到的原因 |
|---|---:|---:|---|
| 日期分区裁剪 | 1.165 | 0.338 | 28文件7天变为4文件1天；任务读字节约4032万降到517万 |
| 小维表广播Join | 1.321 | 1.138 | shuffle读写规模减少；仍受小作业固定开销影响 |
| 热键加盐 | 1.321 | 1.872 | 最大分区变小，但额外读event_id与shuffle使单核环境更慢 |
| 小文件合并64到4 | 1.586 | 0.605 | 文件打开/调度开销减少，90万行逻辑完全一致 |

加盐实验是重要的负结果：最大热点分区从285000降到125641，但额外读取约31.87 MB、shuffle约1.13 MB，单核无法通过增加并行分摊获得收益。面试时应说“验证了倾斜缓解不等于端到端提速，保留未采用原因”。

## 如何阅读执行计划

先看扫描节点有没有PartitionFilters，确认谓词是否能裁剪目录。再看Join是SortMergeJoin还是BroadcastHashJoin，是否广播了真正的小表。看Exchange判断shuffle边界，看AQE是否改写运行时计划。最后用任务指标证实“计划上看起来会优化”在实际输入上发生了。

解释计划中的成本也有边界：文件大小不等于解压后内存，shuffle累计字节不等于同一瞬间占用，整个application wall time不等于某一个SQL耗时。百万扩样记录中memory spill约13.21亿字节、disk spill约4.44亿字节是累计指标，不是新增加的稳定磁盘占用。

## 复现步骤

确认资源门禁和依赖锁，并使用新attempt；这个命令会安排实验资源，不是普通只读查询：

```powershell
uv run python tools/run_scale_guarded.py --events 1000000 --workload optimization --attempt handbook-optimize-001
```

运行后保存收据、Spark计划和原始各轮耗时。预期有效行900000，所有改写等价检查通过，任务无失败。不要只挑最快一轮作为简历数字，也不要把当前电脑换了内存后的新成绩覆盖旧证据。

## 常见误区与排查

“多加分区必然更快”忽略任务调度开销；“广播所有表”可能使executor内存溢出；“看到热点就加盐”忽略聚合是否可两阶段处理；“合并到一个文件最好”忽略下游并行度和超大文件恢复成本。先定位瓶颈，只有与瓶颈相关的变化才值得保留。

如果新一轮差距很大，记录宿主后台负载、VM内存、冷暖缓存、JAR变化与输入hash。若等价失败，停止性能比较，先定位空值、去重顺序、过滤时点或Join基数变化。

## 练习与答案

题：单轮从10秒到3秒，可直接声称性能提升70%吗？答案：先确认同输入同输出、多轮分布、缓存与资源条件、计时边界。可以描述这次观察，但没有这些证据不能推广为稳定提升。

题：加盐让最大分区降低56%，为什么仍不采用？答案：热点负载的下降没有覆盖额外读写和计算成本，尤其只有一个executor核；采用标准应是总体目标改善而非单一中间指标好看。
