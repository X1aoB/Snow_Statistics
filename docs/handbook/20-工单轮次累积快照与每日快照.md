# 20 工单轮次累积快照与每日快照

## 先把业务问题说清楚

一张工单可以创建、处理中、解决、重开、再次解决，最后删除。假设你只保存“当前状态是已解决”，就无法回答：第一次多久解决、重开后又花多久、昨天晚上还有多少积压。不同问题需要保留不同粒度的事实。

本项目的工单来自 **Python 运营模拟器与合成 MySQL/CDC 实验**。两个正式产品没有因为本项目开始收集真实工单、反馈正文或真实客服记录，真实 real 链路也不订阅模拟工单 CDC。简历和面试应说“实现了合成运营数据的工单建模实验”，不能说“已为真实用户上线客服工单分析”。

下面先用三张人工工单手算，再用仅依赖 Python 标准库的 SQLite SQL 重现。不需要打开服务器或虚拟机，不调用任何模型。练习刻意包括重开、未解决删除、普通字段更新、重复投递和回看历史截止日，避免只会算最简单的已解决案例。

## 三种表的粒度：一行究竟代表什么

| 模型 | 唯一粒度 | 回答的问题 |
|---|---|---|
| 状态流转事实 | source + ticket_id + 业务版本；保留源位点 | 工单按什么顺序发生变化？ |
| 轮次累积快照 | source + ticket_id + round | 这一轮何时开始、是否解决、用了多久？ |
| 每日状态快照 | source + ticket_id + 香港业务日期 | 当天结束时是哪个状态？ |

“累积快照”不是对时间一直做 SUM。它是在同一轮生命周期内，逐步补齐开始、处理、解决等里程碑。当前实现通过固定输入重算得到一份运行版本，不意味着已经实现数据库中每轮一行的持续增量 UPDATE。

“每日快照”不是当天发生过的所有状态。工单上午 open、下午 resolved，日末只是一行 resolved。当天解决过几次需要去流转事实或轮次表查，不能 COUNT 日末 resolved 来代替当天解决次数。

```text
模拟器业务事务
  → synthetic CDC：保留创建/更新/删除及源位点
  → 投递去重、版本冲突检查、固定观察范围
  → 有序状态流转事实
      ├─ LAG 比较前态 → 标记开轮 → 累计开轮数 → 轮次快照
      └─ 日期表 × 已创建工单 → 找该日末最后一次变化 → 每日快照
```

## 先手算三张工单

下表统一使用 **香港时间**，完整观察范围截至 `2026-01-05 00:00:00+08:00`，不包含这个瞬间及其后的业务变化。最后一个已完成业务日期是 1 月 4 日。脚本转成 UTC 存储，但显示手算时使用香港时间。

| 工单 | 版本 | 香港发生时刻 | 操作与状态 | 是否开始新轮 |
|---|---:|---|---|---|
| A | 1 | 1 月 1 日 09:00 | 创建 open | 第 1 轮 |
| A | 2 | 1 月 1 日 10:00 | 更新 in_progress | 否 |
| A | 3 | 1 月 1 日 12:00 | 更新 resolved | 否，第 1 轮完成 |
| A | 4 | 1 月 2 日 09:00 | 更新 open | 第 2 轮，重开 |
| A | 5 | 1 月 2 日 10:00 | 更新 in_progress | 否 |
| A | 6 | 1 月 3 日 11:00 | 更新 resolved | 否，第 2 轮完成 |
| A | 7 | 1 月 4 日 09:00 | 删除 d，after 为空 | 否 |
| B | 1 | 1 月 1 日 09:00 | 创建 open | 第 1 轮 |
| B | 2 | 1 月 2 日 12:00 | 更新 in_progress | 否 |
| B | 3 | 1 月 3 日 09:00 | 删除 d，仍未解决 | 否，未解决终止 |
| C | 1 | 1 月 2 日 20:00 | 创建 open | 第 1 轮 |
| C | 2 | 1 月 2 日 21:00 | 更新，状态仍 open | 否，不能把每次 open 都当重开 |
| C | 3 | 1 月 3 日 10:00 | 更新 in_progress | 否，截至观察时点仍未解决 |

额外再投递一次 B 的版本 2，保持相同 Kafka offset；又在另一个 offset 投递相同业务版本和相同内容。原始投递共 15 条，传输重复 1 条，业务版本重复 1 条，合法变化 13 条。真正版本从 1 变到 2 是有效更新，不能因为 ticket_id 相同就去掉。

### 手算轮次答案

| 工单/轮次 | 开始 | 解决或终止 | 已解决耗时 | 截至终止/观察点的经过时间 |
|---|---|---|---:|---:|
| A/1 | 1 日 09:00 | 1 日 12:00 解决 | 3 小时 = 10,800 秒 | 10,800 秒 |
| A/2 | 2 日 09:00 | 3 日 11:00 解决 | 26 小时 = 93,600 秒 | 93,600 秒 |
| B/1 | 1 日 09:00 | 3 日 09:00 未解决删除 | null | 48 小时 = 172,800 秒 |
| C/1 | 2 日 20:00 | 5 日 00:00 观察截止，仍未解决 | null | 52 小时 = 187,200 秒 |

已解决轮次为 2，解决过的工单为 1，重开次数为 1。已解决轮次平均耗时是 `(10800 + 93600) / 2 = 52200 秒 = 14.5 小时`。B 与 C 不应被当作 0 秒解决，也不能把其经过时间塞进“已解决平均耗时”的分母。

A 首次解决为 1 日 12:00，最近解决为 3 日 11:00。若只用“最近解决减首次创建”，会得到 50 小时，包含两轮之间已解决休息的 21 小时；它既不是首轮 3 小时，也不是两轮实际处理历时合计 29 小时。指标名字必须说明计算范围。

### 手算每日快照答案

| 日期 | A 日末 | B 日末 | C 日末 | 积压工单数 |
|---|---|---|---|---:|
| 1 月 1 日 | resolved | open | 尚未创建，没有行 | 1 |
| 1 月 2 日 | in_progress | in_progress | open | 3 |
| 1 月 3 日 | resolved | deleted | in_progress | 1 |
| 1 月 4 日 | deleted | deleted | in_progress | 1 |

本练习把 deleted 作为审计状态继续保留日行，所以快照共 `2 + 3 + 3 + 3 = 11` 行；积压只包含 open 与 in_progress。另一业务也可能要求删除后的日行直接消失，但那是不同契约，不能同时套用两种分母。本项目当前运营日快照也把删除投影为 deleted。

这里的“每日积压”是存量。把四天积压 `1+3+1+1=6` 说成“共 6 张工单”是错误的，因为同一张工单可连续出现在不同日期。

### 第二步：完整程序

```python
"""Synthetic tickets in SQLite memory; no CDC connector, network or service."""
import json
import sqlite3
from datetime import datetime, timedelta, timezone

db = sqlite3.connect(":memory:")
db.row_factory = sqlite3.Row
assert sqlite3.sqlite_version_info >= (3, 25, 0)
HK = timezone(timedelta(hours=8))


def utc(local):
    return datetime.fromisoformat(local).replace(tzinfo=HK).astimezone(timezone.utc).strftime("%Y-%m-%dT%H:%M:%SZ")


db.executescript("""
CREATE TABLE raw(
 delivery INTEGER PRIMARY KEY, source TEXT, topic TEXT, part INTEGER,
 offset INTEGER, ticket TEXT, version INTEGER, at TEXT, op TEXT,
 status TEXT, fingerprint TEXT
);
CREATE TABLE settings(cutoff TEXT);
INSERT INTO settings VALUES ('2026-01-04T16:00:00Z');
""")
changes = [
    (1, "A", 1, "2026-01-01T09:00:00", "c", "open"),
    (2, "A", 2, "2026-01-01T10:00:00", "u", "in_progress"),
    (3, "A", 3, "2026-01-01T12:00:00", "u", "resolved"),
    (4, "A", 4, "2026-01-02T09:00:00", "u", "open"),
    (5, "A", 5, "2026-01-02T10:00:00", "u", "in_progress"),
    (6, "A", 6, "2026-01-03T11:00:00", "u", "resolved"),
    (7, "A", 7, "2026-01-04T09:00:00", "d", None),
    (8, "B", 1, "2026-01-01T09:00:00", "c", "open"),
    (9, "B", 2, "2026-01-02T12:00:00", "u", "in_progress"),
    (10, "B", 3, "2026-01-03T09:00:00", "d", None),
    (11, "C", 1, "2026-01-02T20:00:00", "c", "open"),
    (12, "C", 2, "2026-01-02T21:00:00", "u", "open"),
    (13, "C", 3, "2026-01-03T10:00:00", "u", "in_progress"),
]
# Same transport offset, then the same immutable business version at another offset.
changes += [changes[8], (14, *changes[8][1:])]
for delivery, (offset, ticket, version, local_at, op, status) in enumerate(changes, 1):
    at = utc(local_at)
    fingerprint = json.dumps((ticket, version, at, op, status), separators=(",", ":"))
    db.execute("INSERT INTO raw VALUES (?,?,?,?,?,?,?,?,?,?,?)",
               (delivery, "synthetic", "synthetic.tickets", 0, offset,
                ticket, version, at, op, status, fingerprint))

db.executescript("""
CREATE VIEW transport_ranked AS
 SELECT *,ROW_NUMBER() OVER (
   PARTITION BY source,topic,part,offset ORDER BY delivery) AS transport_rn
 FROM raw;
CREATE VIEW version_ranked AS
 SELECT *,ROW_NUMBER() OVER (
   PARTITION BY source,ticket,version ORDER BY offset,delivery) AS version_rn
 FROM transport_ranked WHERE transport_rn=1;
CREATE VIEW facts AS
 SELECT * FROM version_ranked WHERE version_rn=1
   AND at < (SELECT cutoff FROM settings);
CREATE VIEW ordered AS
 SELECT *,CASE WHEN op='d' THEN 'deleted' ELSE status END AS state,
   LAG(CASE WHEN op='d' THEN 'deleted' ELSE status END) OVER (
     PARTITION BY source,ticket ORDER BY at,version,offset) AS previous_state,
   LAG(version) OVER (
     PARTITION BY source,ticket ORDER BY at,version,offset) AS previous_version
 FROM facts;
CREATE VIEW marked AS
 SELECT *,CASE WHEN state='open' AND
   (previous_state IS NULL OR previous_state='resolved') THEN 1 ELSE 0 END AS starts_round
 FROM ordered;
CREATE VIEW numbered AS
 SELECT *,SUM(starts_round) OVER (
   PARTITION BY source,ticket ORDER BY at,version,offset
   ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS round
 FROM marked;
CREATE VIEW round_base AS
 SELECT source,ticket,round,
   MIN(CASE WHEN starts_round=1 THEN at END) AS opened_at,
   MIN(CASE WHEN state='resolved' THEN at END) AS resolved_at,
   MIN(CASE WHEN state='deleted' THEN at END) AS deleted_at
 FROM numbered GROUP BY source,ticket,round;
CREATE VIEW round_result AS
 SELECT *,
   CASE WHEN resolved_at IS NOT NULL THEN 'resolved'
        WHEN deleted_at IS NOT NULL THEN 'deleted_unresolved' ELSE 'ongoing' END AS outcome,
   CASE WHEN resolved_at IS NOT NULL THEN
     CAST(strftime('%s',resolved_at) AS INTEGER)-CAST(strftime('%s',opened_at) AS INTEGER)
   END AS duration_seconds,
   CAST(strftime('%s',COALESCE(resolved_at,deleted_at,(SELECT cutoff FROM settings))) AS INTEGER)
     -CAST(strftime('%s',opened_at) AS INTEGER) AS observed_elapsed_seconds,
   MIN(resolved_at) OVER(PARTITION BY source,ticket) AS first_resolved_at,
   MAX(resolved_at) OVER(PARTITION BY source,ticket) AS latest_resolved_at
 FROM round_base;
CREATE VIEW daily AS
 WITH RECURSIVE calendar(day) AS (
   VALUES('2026-01-01')
   UNION ALL SELECT date(day,'+1 day') FROM calendar WHERE day<'2026-01-04'
 ), ranked AS (
   SELECT c.day,f.source,f.ticket,f.state,
     ROW_NUMBER() OVER(PARTITION BY c.day,f.source,f.ticket
                      ORDER BY f.at DESC,f.version DESC,f.offset DESC) AS rn
   FROM calendar c JOIN ordered f ON date(f.at,'+8 hours')<=c.day
 ) SELECT day,source,ticket,state FROM ranked WHERE rn=1;
""")


def query(sql):
    return [dict(row) for row in db.execute(sql)]


# Stop rather than silently choose when identical coordinates disagree.
for key in ("source,topic,part,offset", "source,ticket,version"):
    assert db.execute("SELECT COUNT(*) FROM (SELECT 1 FROM raw GROUP BY " + key +
                      " HAVING COUNT(DISTINCT fingerprint)>1)").fetchone()[0] == 0
legal = {None: {"open"}, "open": {"open", "in_progress", "resolved", "deleted"},
         "in_progress": {"in_progress", "resolved", "deleted"},
         "resolved": {"resolved", "open", "deleted"}, "deleted": set()}
for row in db.execute("SELECT * FROM ordered"):
    assert row["state"] in legal[row["previous_state"]], "Illegal ticket transition"
    assert row["previous_version"] is None or row["version"] > row["previous_version"]
raw_count = db.execute("SELECT COUNT(*) FROM raw").fetchone()[0]
change_count = db.execute("SELECT COUNT(*) FROM facts").fetchone()[0]
transport_duplicates = db.execute("SELECT COUNT(*) FROM transport_ranked WHERE transport_rn>1").fetchone()[0]
version_duplicates = db.execute("SELECT COUNT(*) FROM version_ranked WHERE version_rn>1").fetchone()[0]
assert raw_count == 15 and change_count == 13
assert (transport_duplicates, version_duplicates) == (1, 1)
rounds = query("SELECT * FROM round_result ORDER BY ticket,round")
assert [(r["ticket"], r["round"], r["outcome"], r["duration_seconds"], r["observed_elapsed_seconds"])
        for r in rounds] == [("A", 1, "resolved", 10800, 10800),
                             ("A", 2, "resolved", 93600, 93600),
                             ("B", 1, "deleted_unresolved", None, 172800),
                             ("C", 1, "ongoing", None, 187200)]
daily = query("SELECT day,ticket,state FROM daily ORDER BY day,ticket")
assert len(daily) == 11
assert [(r["day"], r["state"]) for r in daily if r["ticket"] == "A"] == [
    ("2026-01-01", "resolved"), ("2026-01-02", "in_progress"),
    ("2026-01-03", "resolved"), ("2026-01-04", "deleted")]
backlog = query("""SELECT day,SUM(state IN ('open','in_progress')) AS backlog
                    FROM daily GROUP BY day ORDER BY day""")
assert [r["backlog"] for r in backlog] == [1, 3, 1, 1]
metrics = dict(db.execute("""SELECT 'resolved_rounds',COUNT(*) FROM round_result WHERE resolved_at IS NOT NULL
 UNION ALL SELECT 'resolved_tickets',COUNT(DISTINCT ticket) FROM round_result WHERE resolved_at IS NOT NULL
 UNION ALL SELECT 'average_resolved_seconds',AVG(duration_seconds) FROM round_result WHERE resolved_at IS NOT NULL
 UNION ALL SELECT 'reopens',SUM(starts_round)-COUNT(DISTINCT ticket) FROM marked"""))
assert metrics == dict(resolved_rounds=2, resolved_tickets=1, average_resolved_seconds=52200.0, reopens=1)
# Rebuild a prior as-of view: no Jan 3 resolution may leak into Jan 2 knowledge.
db.execute("UPDATE settings SET cutoff=?", (utc("2026-01-03T00:00:00"),))
prior = query("SELECT * FROM round_result WHERE ticket='A' ORDER BY round")
assert prior[1]["resolved_at"] is None and prior[1]["latest_resolved_at"] == utc("2026-01-01T12:00:00")
db.execute("UPDATE settings SET cutoff=?", (utc("2026-01-05T00:00:00"),))
print(json.dumps(dict(input_origin="synthetic fixtures", sqlite_version=sqlite3.sqlite_version,
                     raw=raw_count, changes=change_count,
                     transport_duplicates=transport_duplicates, version_duplicates=version_duplicates,
                     rounds=rounds, daily=daily, backlog=backlog, metrics=metrics,
                     prior_as_of_excludes_future_resolution=True), ensure_ascii=False, indent=2))
db.close()
```

## SQL 拆解：为什么这些步骤不能合并成一个 MAX

### 1. 先保留每一个合法版本，再去重

`transport_ranked` 按 topic、partition、offset 去传输重试；同 offset 的内容必须相同，不能只有编号相同就相信它。`version_ranked` 则按 source、ticket、version 去业务版本重放；若相同版本内容冲突，程序停止，不选择最大 offset 掩盖矛盾。

本练习假设版本是同一工单内不可变、严格递增的业务版本，且输入完整。实际 CDC 位点可用来标识变更提交，但不同分区的 offset 不能直接比大小当全局事务顺序。若把所有历史先变成 `ROW_NUMBER() OVER(PARTITION BY ticket ORDER BY version DESC)=1`，A 只剩删除行，两轮历史全部丢失；这个查询适合某些“当前状态投影”，不适合轮次事实。

### 2. LAG 看前态，再标记开轮

`LAG(state)` 是同一工单的上一个状态。只有“此前不存在且当前 open”，或者“此前 resolved 且当前 open”，才将 `starts_round` 置为 1。C 的 open → open 是原轮更新，标记仍为 0。用累计 SUM 得到轮次 1、2……，所以每一条处理中、解决、删除变化都能归入所处轮次。

窗口中明确写了 `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`，表示逐行累计。这样不会不小心使用某些引擎默认 RANGE 框架，把同时间的多条记录合并为同一位置。仍要保证排序键能表达提交顺序；本例有版本和 offset 决胜，真实工程需要相应来源保证。

### 3. 按轮聚合里程碑，区别解决和删除

`MIN(CASE WHEN starts_round=1 THEN at END)` 找本轮开始；`MIN(CASE WHEN state='resolved' THEN at END)` 找本轮首次进入解决。仅更新 resolved 工单的其他属性不应重新计算一遍解决时间。删除不自动补 resolved_at，因此 B 是未解决终止，duration_seconds 仍为 null。

本教学表另外保留 deleted_at 和 outcome。A 第二轮先解决后删除，所以 outcome 仍是 resolved，删除发生在解决以后；它不撤销那次历史解决。当前 Python 基准只在删除时仍有 active 轮次才记录 deleted_at，而 Spark 当前轮次表没有这个字段。因此，本教学字段属于解释用扩展，不能声称已有 Spark 表与它逐字段相同。

### 4. 日期表先生成应观察的日期，再找最后状态

递归 CTE 生成 1 至 4 日。每天与该日期及以前的状态变化连接，按时间、版本倒序取一条。C 在 1 日没有任何已发生变化，所以不会造一行 open 或 deleted。B 在 3 日删除后，4 日仍以删除状态保留审计行；这是本章的明确规则。

生成时间不等于业务时间。如果 5 日才运行 2 日的回补，应只使用那个截止范围内的状态，再生成 2 日日末快照，而不是拿今天状态填回过去。晚到更正是否改写历史，要建立新的运行/发布版本，不能覆盖旧回执并假装当时就知道。

### 5. 首次与最近解决也有观察时点

`first_resolved_at` 与 `latest_resolved_at` 在同一工单的所有轮次上重复，便于使用，但它们是本次固定截止范围下的工单级属性。不能把 4 日计算得到的最近解决时间当作 1 日当时已知状态。脚本临时把 cutoff 调整到 3 日 00:00 HKT，再检查 A 第二轮仍未解决，随后恢复原值；只修改内存练习设置，不修改真实清单或保留期限。

## 更新、删除和重开最容易混淆的边界

| 场景 | 本章明确规则 | 项目中应如何表述 |
|---|---|---|
| open → open | 同轮更新，不加 round | 状态相同不意味着整条 CDC 无效，其他属性可能变了 |
| resolved → open | 新轮、重开次数加 1 | 不覆盖第一轮耗时 |
| resolved → resolved | 同一已解决轮的更新 | 保留本轮首次解决时刻 |
| open / in_progress → delete | 未解决终止 | 不计成功解决，不当作 0 秒解决 |
| resolved → delete | 历史解决事实仍成立 | 当前在册数与历史解决数是不同指标 |
| delete 后同 ID 再创建 | 本练习拒绝 | 需要新实体代际/新 ID 或明确恢复契约，当前未验证通用复活模型 |
| 首条就是 resolved | 本练习拒绝 | 可能输入缺历史，不能补造 opened_at |
| 同版本内容不同 | 本练习拒绝 | 不能靠最新 offset 吞掉冲突 |
| 同时刻多次更新 | 依赖受控版本/位点排序 | 时间戳本身不足以唯一排序 |
| 删除消息的 after=null | 用 op=d 识别删除 | NULL 不能被误认作普通未知状态 |
| Kafka tombstone value=null | 不当作又删除一次 | 与有内容的 CDC 删除事件区分，见第 15 章 |

本教学数据不覆盖暂停计时、节假日工作时长、多个处理人、SLA 违约、撤销解决等业务。这里的 duration 是墙上时钟经过秒数，不是客服实际劳动时长。若面试被问到，应先说明边界，再解释如何增加状态与口径，不能说“通用工单系统已经支持”。

## 检查方法与排障

按四个粒度逐层检查：15 条原始投递 → 13 条版本事实 → 4 个处理轮次 → 11 行每日快照。层与层之间不是都要求行数相等，但每个差异都必须能解释。重复、轮次合并和日历扩展会分别减少或增加行数。

若想看到累计轮次，可在程序末尾 `db.close()` 之前插入：

```python
print(query("SELECT ticket,version,state,previous_state,starts_round,round FROM numbered ORDER BY ticket,version"))
print(query("SELECT day,state,COUNT(*) AS tickets FROM daily GROUP BY day,state ORDER BY day,state"))
```

| 错误表现 | 常见原因 | 检查方法 |
|---|---|---|
| A 只有一轮 | 按 ticket 取最新行后才建模 | 检查 facts 是否还保留 7 个 A 版本 |
| C 有两轮 | 每次 open 都标记开始 | 检查 previous_state 和 starts_round |
| 解决耗时变成 50 小时 | 最近解决减首次创建 | 先按 ticket + round 分组 |
| 平均值很低 | 未解决 null 被 COALESCE 成 0 | 分母只选 resolved_at 非空轮次，并单列未解决数 |
| 日末累计数突然下降 | 删除行直接被丢掉但分母定义未变 | 查 daily 的 deleted 投影与当前在册定义 |
| 1 日出现 C | 日期交叉连接没有过滤创建前 | 只匹配当天及以前已发生的事实 |
| 回看 2 日竟然知道 3 日解决 | 未先限制 cutoff | 先构建 as-of 输入，再算首次/最近解决 |
| 轮次号 0 或无 opened_at | 输入缺创建、非法状态变化 | 拒绝发布并检查输入覆盖，不自动补一条创建 |
| 来源混入 real | 忽略来源过滤 | 教学全部 synthetic，真实链路不接工单 CDC |

本例用日历结束日固定为 1 月 4 日，临时 as-of 检查只验证轮次不泄露未来信息。如果把程序改成通用报表工具，还须让日历结束日与观察截止同步；不要将固定练习程序直接用来生成任意日期的“正式日末快照”。

## 练习与逐步答案

1. **只看 1 月 2 日日末，A 的首次解决与最近解决是什么？** 都是 1 月 1 日 12:00 HKT；第二轮未解决。程序的 prior_as_of 断言验证这一点，不能把 3 日 11:00 放进来。
2. **删掉重复投递的两行会怎样？** raw 从 15 变成 13，transport_duplicates 和 version_duplicates 分别从 1 变成 0；13 条有效变化、4 轮、11 日行与所有业务指标不变。先改输入和原始条数断言，不应改手算业务答案。
3. **把 C 第二条 open 改成 resolved，然后原 3 日 in_progress 怎么办？** 这会成为 resolved → in_progress，违反本例规则；断言应失败。若业务要重新处理，应先显式重开 open，不能默默猜它的意思。
4. **A 1 月 3 日又解决一次后，解决工单数是多少？** 整个观察范围只有 1 个 distinct ticket 解决过；已解决轮次是 2。若按日期看“当日有解决的去重工单数”，1 日和 3 日各为 1，跨日相加仍不是全窗口 2 张工单。
5. **B 删除是否降低 1 月 1 日积压？** 不会。1 日结束时 B 确实未解决；3 日删除影响此后日快照和当前在册，不倒改历史事实。
6. **为什么不能用 COUNT(resolved_at) / COUNT(ticket) 随意算解决率？** 在轮次表上 ticket 重复，分母是轮次；在工单表上每票一行，分母是工单。先声明“已解决轮次占已开始轮次比例”或“曾解决工单占已创建工单比例”，再选择同粒度的分子分母，并说明删除/未成熟样本如何处理。
7. **若只保留当前表，能补回所有轮次吗？** 不能。当前 resolved 不包含历史重开和每轮开始时间。需要可用的 CDC 历史、状态事实或已经保留的聚合辅助状态；缺失历史必须标记不完整。

面试讲解可按这个顺序：“先明确工单可以重开，因此一张当前状态表不足；流转事实保留变化，累积快照按处理轮次记录里程碑，每日快照记录日末存量。重开开新轮、删除不算解决、未解决耗时保留 null。我的项目使用合成运营 CDC 验证这些模型，与正式访问统计来源隔离；特定状态边界及各引擎实现范围以实际测试为准。”
