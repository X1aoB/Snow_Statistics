# 35 面试讲解、简历表述与追问答案

## 一分钟讲清楚项目

可以这样组织：“我已有个人网站和小吉终端，希望了解页面、角色和渠道的使用情况，同时练习数据开发。我做了独立可关闭的统计服务，访问事件在用户同意后采集，服务质量来自独立披露的脱敏完成日志。基础统计由Python和SQLite持续维护，公开页有延迟和小样本保护；本机按需把数据同步到Kafka，完成Spark离线建模和Flink实时实验。运营部分用固定种子合成MySQL业务、CDC、SCD2与工单快照。所有大数据组件都可停止，原产品和公开基础统计不依赖它们。”

这段表达同时交代业务动机、数据来源、工程边界和实验性质。生产接入状态应按实际发布证据替换，不把候选代码当作已经上线。

## 十分钟展示结构

```mermaid
flowchart LR
  B[1分钟 业务与约束] --> A[2分钟 架构和解耦]
  A --> M[2分钟 口径与建模]
  M --> R[2分钟 重放恢复与对账]
  R --> O[2分钟 性能及负结果]
  O --> L[1分钟 局限和后续]
```

先展示两站和三模式架构，接着用一条事件贯穿接收、聚合、同步、分层和发布。模型挑一个能讲透的SCD2或工单重开，不一口气报所有组件名字。恢复部分展示同一输入重复导入前后整数指标不变。优化部分展示分区裁剪和加盐变慢两个结果，结尾解释小数据和单宿主限制。

## 高频追问与回答思路

**为什么真实数据小还用Hadoop？** 线上部分按小流量设计，Hadoop等用于可复现学习和求职实践，按需启动；我没有把它们作为生产低量业务的必需组件。用合成扩样验证方法，明确资源与规模。

**如何保证Exactly Once？** 不用一句总口号覆盖全链路。浏览器发送允许丢失；接收持久化后确认；同步本地先落批次再Kafka确认，失败允许重放；状态Checkpoint、Doris事务和业务键去重分别验收。端到端以相同cutoff下业务指标对账作为证据。

**event_id和request_id为何都要？** event_id识别同一统计事件重发；request_id识别同一业务请求的完成事实。不同event_id可能指向同一request_id，若只去重事件仍会把一个请求算多次。

**SCD2为什么用左闭右开？** 变更时间点只属于新版本，避免边界两次匹配。按发生时分类与按当前分类回答不同问题；事实与维表Join必须检查区间不重叠。

**数仓停止后统计页怎么办？** 基础聚合一直由轻量SQLite生成，完整数仓只读增量；停止Kafka/Flink/Spark不会改变公开页来源。原产品通过可选适配器隔离故障，业务不等待统计。

**迟到超过十分钟怎么办？** 实时旁路进入离线校正，默认重算最近七天，显式历史补数另行处理。要考虑源保留期和输入覆盖，超过保留窗口丢失的数据不能凭空恢复。

**为什么UV不是人数？** 它是按应用/日期/有效匿名标识去重的观察计数，受同意、清除标识、跨设备和拦截影响，不合并自然人身份，也不把每日UV相加当区间UV。

**血缘做到哪一层？** 核心三个任务显式表级映射并实际读回Marquez；不声称全链路自动或列级。强制kill留下START时保持未知，通过权威状态补失败，不靠文件存在伪造成功。

## 面试中的风险表述

| 不建议说 | 可以准确说 |
|---|---|
| 生产百万用户 | 百万条固定合成输入的离线实验 |
| 三机容灾 | 同宿主虚拟节点的软件故障与恢复实验 |
| 完全匿名 | 独立匿名标识、白名单和保留限制，仍有可链接风险 |
| 端到端零丢失 | 明确各段确认/重放/丢弃边界并做业务对账 |
| 加盐优化成功 | 热点减小但单核耗时变差，保留未采用依据 |
| 所有请求成功率 | 已记录的服务端生成完成事件成功比例 |

## 自测与答案标准

脱离代码，用纸画出事件ID、请求ID、匿名ID、会话ID和jump ID分别在哪生成、在哪里使用、多久保留。答案应能说明两站不共享匿名ID、请求完成仅由可信服务端计量、入口只归因最近有效点击。画不清时回看第04、05、07、22章。

最后准备一次三分钟故障复盘：故障是什么、如何观察、错误假设是什么、最后修复为什么有效、还有什么没测。允许讲失败，关键是证据和判断过程。
